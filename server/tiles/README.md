# tiles

CMS のアセットをタイル配信用の設定に変換するパッケージ。CMS の `tiles` モデルから取得したアセット URL のファイル名を解析して、z/x/y 範囲付きの `Tiles` マップにまとめ、必要に応じて Rust 製タイルサーバー（`/tile`）の `config.json` 形式に変換する。

## アセット名による z/x/y 範囲指定

アセットのファイル名（ベース名、拡張子を除く）に `_` 区切りで `z` / `x` / `y` プレフィックス付きのパートを含めると、そのアセットが配信するタイル範囲を制限できる。実装は `tiles.go` の `extractRange` / `extractRangePart`。

### フォーマット

```
<任意のベース名>_z<範囲>_x<範囲>_y<範囲>.<拡張子>
```

- `_` で分割した各パートを順にスキャンし、`z` / `x` / `y` で始まるものを拾う
- 範囲指定の書式は 2 通り：
  - **単一値**: `z5` → `ZMin = ZMax = 5`
  - **範囲**: `z5-15` → `ZMin = 5`, `ZMax = 15`（`min > max` なら自動で入れ替わる）
- 順序は問わない。指定が無い軸は `-1`（= 制限なし）になる
- パースに失敗した軸（数値以外、`-` が複数など）は制限なし扱い

### 例

| ファイル名                        | 効果                                    |
| --------------------------------- | --------------------------------------- |
| `ortho_z10-15.zip`                | z = 10〜15 のみ配信                     |
| `dem_z14_x100-200_y50-80.zip`     | z=14、x=100〜200、y=50〜80              |
| `building.tif`                    | 範囲制限なし（COG はそのまま配信）      |
| `chizu_z18.zip`                   | z=18 のみ                               |

### 配信時のマッチング

`Tiles.Find(name, z, x, y)` が、同名アセットの登録順に `Range.In(z, x, y)` で先頭から一致するものを返す。複数のファイルを並べて高ズーム／低ズームを使い分けるときは、**より具体的な範囲のものを先**に登録する想定。

## アセット URL の扱い

`assetBaseURL` が拡張子を見て分岐する：

- `.tif` / `.tiff` → COG として **URL をそのまま保持**
- それ以外（典型的には `.zip` で展開済みの XYZ タイル群）→ **拡張子を除いた URL** をベースとして保持し、配信時に `{z}/{x}/{y}.png` を付け足す

## タイルサーバー設定への変換

`Tiles.ToTileServerConfig(baseURL)` が `/tile`（Rust）の `config.json` スキーマ（`TileServerConfig`）に変換する：

- `.tif` / `.tiff` → `type: "cog"`、`url` はそのまま、`order` は登録順
- それ以外 → `type: "xyz"`、`url` は `…/{z}/{x}/{y}.png` テンプレート、ファイル名から拾った範囲を `range` フィールド（`z_min` / `z_max` / `x_min` / `x_max` / `y_min` / `y_max`）に詰める
- 加えて MapLibre スタイル `dark-map` / `light-map` を `<baseURL>/tiles/styles/<name>` 参照で追加

つまり「ファイル名で範囲指定」は `server/tiles` 側の規約で、Rust 側の `config.json` の `range` フィールドにマッピングされる仕組み。

## キャッシュとリフレッシュ

CMS から取得した `Tiles` はメモリにキャッシュされ、TTL は **3 分**（`tilesTTL`）。`/tiles/config.json` のリクエスト時に TTL が切れていれば CMS から再取得する遅延更新方式。

- 起動時に `Init` が一度同期で取得してキャッシュをウォームアップする
- TTL 内のリクエストはキャッシュをそのまま返す（CMS にアクセスしない）
- TTL 切れのリクエストは CMS から再取得してキャッシュを更新
- 同時に複数リクエストが TTL 切れにヒットしても `refreshLock` で直列化し、CMS への問い合わせは 1 回だけに収束する
- CMS への再取得が失敗した場合はエラーログを出して**直前のキャッシュをそのまま返す**（503 で /tiles/config.json を空にしないため）

つまり CMS で tiles モデルのアセットを更新しても、最大で 3 分はサーバーに反映されないことがある。即時反映が必要な場合はサーバーを再起動する。
